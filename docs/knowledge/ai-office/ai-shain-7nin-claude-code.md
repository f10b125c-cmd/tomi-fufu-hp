# Claude Codeで「AI社員7人体制」を作り、月120時間を削減する方法

- **出典**: [Claude code研究ラボ (@claudecode84) のポスト](https://x.com/claudecode84/status/2087805485701644461)（2026年8月13日）
- **対象**: 非エンジニアがClaude Codeで役割定義済みの「AI社員」を複数体構築し、日常業務を自動化する手順
- **用途**: AIオフィスの組織設計（役割定義・共通ルール・フォルダ構成・失敗パターン）のリファレンス

## 要旨

非エンジニアの筆者が、Claude Codeで「リサーチ」「ライター」「営業」「経理」「秘書」「戦略」「校閲」の7つの役割を持つAI社員を構築し、月120時間分の外注・自作業務（月18万円相当）を、月3,000円のAPI費用＋Claude Pro契約だけで代替している事例。プロンプトの工夫ではなく「役割・判断基準・ツール・手順・保存場所を事前に定義したエージェントに指示一発で最後まで走らせる」設計思想が核。

## AI社員とチャットAIの違い

チャットAIへの「相談」は、コピペ・整形など人間の作業が残る。AI社員は以下2点が決定的に違う。

1. **ファイルを読み書きできる**: Claude Codeはターミナル上でフォルダを直接操作し、成果物がそのままファイルとして残る（コピペ不要）。
2. **記憶が蓄積する**: 事業内容・トーン・NGリストなどの前提知識をファイルに書いておけば、AI社員は起動のたびに読み込む。毎回の説明コスト（体感1日30分＝月15時間相当）がゼロになる。

## セットアップ（所要30分）

1. PC（Win/Mac）を用意
2. Claudeの有料プラン契約
3. ターミナル（Mac標準 / WindowsはPowerShell）
4. Node.jsをインストール
5. 空フォルダを1つ作成（例: デスクトップに `ai-company`。日本語名は避ける）
6. そのフォルダでClaude Codeを起動しログイン
7. 動作確認として「このフォルダに hello.md を作って、中に『AI社員第一号、稼働開始』と書いてください」を実行

## 設計フェーズ（ここを飛ばすと失敗する）

いきなりプロンプトを書かず、まず**棚卸し**をする。

### ステップ1: 1週間の作業を全部書き出す

「メールを返した」レベルの粒度で全部書く（筆者の例: 47項目）。

### ステップ2: 4象限に分類する

| 象限 | 条件 | 対応 |
|---|---|---|
| A | 毎回同じ手順 × 判断不要 | 即AI化。最優先 |
| B | 毎回同じ手順 × 判断が要る | AIが下書き、人間が決定 |
| C | 毎回違う × 判断不要 | AIに部分的に任せる |
| D | 毎回違う × 判断が要る | 人間がやる。触るな |

筆者の内訳: A19件 / B14件 / C8件 / D6件。

### ステップ3: A（＋B）の項目を役割ごとに束ねる

「誰の仕事か」でグループ化すると自然に部署ができる。筆者は最終的に**7人**で構成（リサーチ・ライター・営業・経理・秘書・戦略・校閲）。

**なぜ最初から大人数を作らないか**: 筆者は最初12人作り、1週間後に使っていたのは3人だけだった。**「3人で始めて、詰まったら1人足す」**が正解。定義書を書く前に「この社員を今週何回呼ぶか」を数字で見積り、3回未満なら作らない。

## フォルダ構成

```text
ai-company/
├── CLAUDE.md          ← 全社共通ルール
├── agents/            ← 社員一人ずつの定義書
│   ├── researcher.md
│   ├── writer.md
│   ├── sales.md
│   ├── accounting.md
│   ├── secretary.md
│   ├── strategist.md
│   └── editor.md
├── knowledge/         ← 会社の前提知識
│   ├── business.md
│   ├── tone.md
│   ├── ng-list.md
│   └── lessons.md
├── templates/         ← 成果物のひな形
└── output/            ← 成果物の保存先
    ├── reports/
    ├── drafts/
    └── invoices/
```

### CLAUDE.md（全社共通ルール）の例

Claude Codeはフォルダ直下の `CLAUDE.md` を起動時に自動で読み込むため、ここが「就業規則」になる。**個別の役割定義書より先にこれを書く**（順番を間違えると口調がバラバラになり手戻りが発生する）。

```text
# 全社共通ルール

## 事業概要
knowledge/business.md を必ず読んでから作業を始めること。

## 出力の原則
- 成果物は必ず output/ 配下にファイルとして保存する
- チャット欄に長文を貼るな。ファイルに書け
- ファイル名は日付+内容(例:2026-04-12_competitor.md)
- 保存後、保存先パスと要約3行だけを報告する

## 絶対禁止
- 出典のない数字を書くこと
- 「〜と言われています」で曖昧に逃げること
- 私に確認せず既存ファイルを上書きすること
- 依頼されていない作業を勝手に足すこと

## 不明点があるとき
推測で埋めるな。作業を止めて質問しろ。
質問は最大3つまでにまとめること。

## 完了報告の形式
1. やったこと(1行)
2. 保存先パス
3. 気になった点 or 懸念(必ず1つ以上)
```

「懸念を必ず1つ以上」を入れることで、AIが自分の成果物を批判的に見直すようになり、体感で品質が2割向上したとのこと。

### knowledge/ ファイル

- `business.md`: 事業内容・ターゲット像・提供価値・価格帯・実績数字
- `tone.md`: 文章トーン（例:「1文40字以内」「専門用語は初出時に注釈」「語尾に『!』は使わない」「絵文字は使わない」）
- `ng-list.md`: 禁止表現（例:「必ず稼げる」「誰でも簡単に」「絶対」）
- `lessons.md`: AIが起こした失敗ログ（後述）

## AI社員7人の役割定義（要点）

各定義書は「役割 / 行動原則 / よくある失敗と対策 / 出力先」の型で統一されている。

### 1. リサーチ担当 (researcher.md)
情報収集専門。情報源は `knowledge/sources.md` のリストに限定、直近7日以内のみ、過去レポートと重複除外、出典URL必須、重要度A/B/C判定。**最大7項目までに制限**（無制限だと30項目のリストを作ってきて読まれなくなる）。出力先: `output/reports/YYYY-MM-DD_research.md`

### 2. ライター担当 (writer.md)
**下書き専門。完成品は作らない**（人間が最後の一筆を入れることで「自分の言葉」を保つ）。トーン参照必須、冒頭3行に数字2つ以上、抽象語で書き出し禁止、出力は必ず3案で切り口を変える（体験談／逆張り／数字提示、と型を固定）。

### 3. 営業担当 (sales.md)
提案の骨組みのみ作成、売り込み文は書かない。相手の課題仮説3つに根拠を紐付け、「課題→解決策→想定効果」の順で構成。**金額は自分で決めず空欄にして人間に投げる**。

### 4. 経理担当 (accounting.md)
数字の整理のみ、**判断はしない**。テンプレート厳守、計算は必ず2回検算、数字が合わなければ推測で埋めず作業停止、税務判断はせず「要確認」マークで人間に回す。経費区分の勝手な判定・端数の勝手な丸めは絶対禁止。数字・法律が絡む領域は人間の検品を必須にする設計。

### 5. 秘書担当 (secretary.md)
`output/` 配下の未完了タスクを毎朝拾い、**「今日やるべき3つ」に絞る**（4つ以上出さない）。理由を1行ずつ添え、期限超過タスクは強調表示。

### 6. 戦略担当 (strategist.md)
**私の考えを疑うのが仕事**。提案に対し必ず懸念を3つ、確率と損失規模付きで挙げる。「良いと思います」だけの返答は職務放棄とみなす、と明記。筆者はこの担当の指摘で3回企画を中止し、無駄な出費を回避。

### 7. 校閲担当 (editor.md)
公開前の最終関門。数字の出典・NGワード・語尾の連続・1文60字超・主語欠落をチェック。**「該当行/問題/修正案」の3列で列挙するのみで、本文を勝手に書き換えない**（書き換えると気づかず公開してしまうため）。

**追加チェック項目（[129文字ポストの分析](./copywriting-129char-hook-breakdown.md)より）**: 反証不可能な言い切り（トートロジー）を鋭い洞察として提示していないか。「結果が出る人は結果が出る行動をしている」のような同語反復は、当たり前すぎて反証しようがないだけであり、真の洞察ではない可能性がある。自社発信でこの型の文章を使う場合、**言い切りの裏に検証可能な根拠があるか**を校閲担当が確認する。根拠がなければ「鋭い指摘」ではなく「空虚な具体性」として扱い、修正案を提示する。

## 実際の1日の運用フロー（時間軸）

| 時刻 | 内容 | 削減効果 |
|---|---|---|
| 7:00 | 「今日の朝会をやって」→秘書が重要タスク3つと期限切れ警告を提示 | - |
| 7:10 | 「今日のリサーチ、いつもの形式で」を投げて放置、A項目だけ読む | 情報収集: 月12時間削減 |
| 8:00 | リサーチのA項目から発信ネタを選び「投稿案3つ」を依頼、自分の体験を1段落足して仕上げる | 下書き: 月28時間削減 |
| 10:00 | 「このリストの5社分、提案の骨組みを作って」 | 営業準備: 月45時間削減 |
| 14:00 | 新企画を戦略担当に「懸念を3つ出して」で壁打ち | - |
| 18:00 | 「output/drafts/の今日の分、全部チェックして」で校閲 | 校閲: 月13時間削減 |
| 月末 | 「今月の請求書、5件分作って。検算結果も出して」（数字は必ず自分で全部確認） | 経理: 月14時間削減 |

タスク整理で月8時間削減も含め、**合計月120時間**（20営業日で1日6時間相当）を削減。

## 踏んだ5つの失敗

1. **社員を12人作って9人使わなかった** → 定義書を書く前に「今週何回呼ぶか」を数字で見積る。3回未満なら作らない。
2. **指示が曖昧で的外れな成果物が量産された**（例: 「いい感じの投稿書いて」） → 曖昧さはAIでなく設計の責任。「誰に」「何を思わせたいか」「文字数」「NG表現」を定義書に書き切る。
3. **確認せず信じて、実在しない市場規模の数字を公開してしまった** → AIは案を作るプロだが責任を取るプロではない。数字と固有名詞は必ず自分の目で出典確認。訂正投稿で信用が削れた実例あり。
4. **全社ルールを作らず、社員ごとに口調がバラバラになった** → 個別定義書より先にCLAUDE.md（全社共通ルール）を書く。順番を間違えると二度手間になる。
5. **一度作って2ヶ月放置し、情報が古くなった**（価格改定前の価格で提案書を作成） → 月1回 `knowledge/` を更新する。これがAI組織の「教育」。

## 精度を上げる7つの小技

1. 「懸念を必ず1つ出せ」を全社ルールに入れ、AIの自己批判を強制する
2. 数値の上限を必ず切る（「最大7項目」「3案まで」「1文60字以内」など。制限がないと膨らんで読まれなくなる）
3. 「わからないなら止まれ」を明記する（AIは空白を推測で埋める性質があり、これが最も危険）
4. 良い出力を `templates/` に保存し、「templates/best_report.md と同じ構成で」で再現する
5. 1チャット1タスクを守る（複数の大きな仕事を1会話に詰めると前提を引きずって混乱する）
6. 出力は必ず「ファイルに書け」と指示する（チャット欄への長文出力はコピペ作業を生み、工数削減にならない）
7. 週1回、`knowledge/lessons.md` に失敗ログを書き足し、CLAUDE.mdに「作業前にlessons.mdを読め」と明記する（同じミスの再発防止。筆者いわく最も効果が大きい）

## 3日で構築するロードマップ

**1日目（2時間）**: Node.js/Claude Codeインストール(30分) → hello.md動作確認(5分) → 1週間の作業書き出し(45分) → 4象限分類(30分)。**この日は社員を作らない**。棚卸しだけで終える。

**2日目（3時間）**: フォルダ構成作成(15分) → CLAUDE.md作成(45分) → `knowledge/business.md`・`tone.md`作成(60分) → **社員は3人だけ**作成(60分)。選び方は「一番時間を食っている作業の担当」。

**3日目（2時間）**: 3人に実際の仕事を投げる → 成果物のダメな点を全部メモ → 定義書に反映 → もう一度投げる。この「投げる→直す→投げる」を2周やる（1周目で諦める人が多いが、1周目は微妙で普通）。

**4日目以降**: 毎日使う。詰まったら社員を1人足す。月1回 `knowledge/` を更新する。

## 要点まとめ

1. AI社員とチャットAIの違いは「ファイルを触れる」「記憶が蓄積する」の2点
2. 準備は30分。Node.js＋Claude Code＋空フォルダだけ
3. プロンプトを書く前に、1週間の作業を棚卸しして4象限に分類する
4. CLAUDE.md（全社ルール）を個別定義書より先に書く
5. 社員は3人から始める。12人作ると9人使わない
6. 数字と法律の領域は必ず人間が検品する。ここを飛ばすと事故る
7. 月1回 `knowledge/` を更新する。これがAI組織の教育

## AIオフィスへの適用メモ

- 役割定義のテンプレート（役割／行動原則／よくある失敗と対策／出力先）は、そのまま自社のエージェント定義フォーマットとして流用できる。
- 「完成品を作らせない」（ライター・校閲）、「判断させない」（経理）、「懸念を強制的に出させる」（戦略）という**役割ごとの権限制限の設計**は、[宮本佳林さんの事例](./vibe-coding-miyamoto-kanon.md)の「フォールバック設計」「複数AI相互監査」とも通じる考え方。人間の最終確認ポイントを役割定義の中に明示的に組み込むことが共通の勘所。
- 数字・固有名詞の出典未確認による誤情報公開の実例は、AIオフィス運用時の必須チェック項目として社内ルールに反映する価値がある。
