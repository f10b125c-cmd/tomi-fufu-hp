# Claude Codeプロジェクトの解剖学：リポジトリ構造の設計指針（事実確認済み）

- **出典**: X投稿（ユーザー提供テキスト、URLなし、2026年8月25日受領）＋ インフォグラフィック画像「Claude Code プロジェクト構成」（作成者: Brij Kishore Pandey）
- **内容**: 「良いプロンプトを書くこと」より「Claudeがエンジニアのように動ける構造をリポジトリ側に用意すること」が重要だという主張と、そのための5要素の解説
- **検証**: 新規に登場した技術的主張（サブディレクトリ配置のローカルCLAUDE.md）はclaude-code-guideで公式ドキュメントと照合済み。**REAL（実在する機能）と確認**。

## 核となる主張

> リポジトリが乱雑ならClaudeはチャットボットのように動く。構造化されていれば、コードベースの中に住む専属エンジニアのように動き始める。
> プロンプトは一時的。構造は永続的。

必要なのは以下の4つの情報をリポジトリ側に用意すること。

- **Why**: このシステムは何のためにあるか
- **Map**: 何がどこにあるか
- **Rules**: 何をしてよくて、何をしてはいけないか
- **Workflows**: 仕事をどう進めるか

## Claude Codeプロジェクトの解剖学（5要素）

### ① CLAUDE.md ＝ プロジェクトの記憶

長くしすぎない。基本的に入れるのは以下の3つ。

- Purpose（目的）
- Repo map（リポジトリの構造）
- Rules / commands（ルール・コマンド）

情報量より、**重要な情報がすぐ見つかること**の方が大事。（[初心者向け教科書](./claude-code-beginner-textbook.md)で確認した「200行以下」の公式ガイドラインとも整合する）

### ② `.claude/skills/` ＝ 再利用できる専門モード

コードレビュー、リファクタリング、デバッグ、リリース手順など、毎回同じプロンプトを書くような定型業務をSkillとして持たせる。必要なときにClaudeがすぐ専門モードへ入れるようになる。

### ③ `.claude/hooks/` ＝ 自動で効くガードレール

Claudeは指示を忘れることがあるが、Hooksは忘れない。例: 編集後の自動フォーマット、重要変更後の自動テスト実行、機密フォルダへの変更制限。「必ず守ってほしいこと」を自動化する仕組み（[MCPツール自動化事例集](./mcp-tools-automation-50.md)の安全装置6項目、[初心者向け教科書](./claude-code-beginner-textbook.md)のHooksの説明とも一致）。

### ④ `docs/` ＝ 必要なときに読むコンテキスト

全てをCLAUDE.mdやプロンプトに詰め込む必要はない。アーキテクチャ概要、設計判断、運用手順といった情報はdocsに置く。**Claudeは全部を覚える必要はなく、正しい情報がどこにあるかが分かればよい**という考え方。

### ⑤ ローカルCLAUDE.md ＝ 重要エリア専用のルール（実在確認済み）

複雑な場所には、その場所専用のコンテキストを置く。

```text
src/auth/CLAUDE.md
src/persistence/CLAUDE.md
infra/CLAUDE.md
```

**claude-code-guideによる検証結果（REAL）**: サブディレクトリへのCLAUDE.md配置は、Claude Code公式ドキュメントに明記された実在の機能。

- ルート（および現在の作業ディレクトリの祖先パス）にあるCLAUDE.mdは**起動時に読み込まれる**
- **サブディレクトリのCLAUDE.mdは、Claudeがそのサブディレクトリ内のファイルを読んだタイミングでオンデマンドに読み込まれる**（起動時に一括読み込みされるわけではない）
- 読み込まれた複数のCLAUDE.mdは連結されて使われる。サブディレクトリのCLAUDE.mdは上位のルールを**上書きするのではなく追加する**

これにより、Claudeはその領域特有のルールや注意点を理解した状態で作業できる。

## インフォグラフィックで示されていたリポジトリ構成例

```text
claude_code_project/
├── CLAUDE.md
├── README.md
├── docs/
│   ├── architecture.md
│   ├── decisions/
│   └── runbooks/
├── .claude/
│   ├── settings.json
│   ├── hooks/
│   └── skills/
│       ├── code-review/SKILL.md
│       ├── refactor/SKILL.md
│       └── release/SKILL.md
├── tools/
│   ├── scripts/
│   └── prompts/
└── src/
    ├── api/CLAUDE.md
    └── persistence/CLAUDE.md
```

インフォグラフィック内のベストプラクティス（要約）:

- CLAUDE.mdは簡潔かつ構造化して保つ
- 繰り返しのAIワークフローにはSkillを使う
- 自動化とチェックにはHookを使う
- アーキテクチャの判断は`docs/decisions/`のような場所に記録する
- モジュール型のリポジトリ設計を維持する（モジュールは小さく保つ）

## AIオフィスへの適用メモ

- この5要素（CLAUDE.md／Skills／Hooks／docs／ローカルCLAUDE.md）は、[Claude Code初心者向け教科書](./claude-code-beginner-textbook.md)の内容とほぼ完全に整合しており、**Claude Codeプロジェクトの標準的なディレクトリ設計指針**として信頼して使える。
- 「常識はCLAUDE.md、手順はSkill」（初心者向け教科書）に加えて、「**エリア固有のルールはローカルCLAUDE.md**」という第3の区分が明確になった。大規模なコードベース・複数チームが関わるAIオフィスの構築時は、この3分類（全社共通CLAUDE.md／再利用手順Skill／エリア別ローカルCLAUDE.md）を意識してファイルを配置するとよい。
- `docs/decisions/`のような「設計判断の記録場所」を用意する発想は、AIオフィスが長期運用される中で「なぜこの設計にしたか」をAI自身が後から参照できるようにするために有効。
