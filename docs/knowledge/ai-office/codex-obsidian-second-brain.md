## Claude Code×Obsidian運用で挙がっていた課題（要検証）

1. Vaultが大きくなるとコンテキストウィンドウの消費が大きい（「クエリ1回でコンテキストの30%消費」「Codexの3.2〜4.2倍のトークン消費」という主張は未検証）
2. サブスクリプションの利用制限（記事は「5時間ローリング制限」と表現）が、Vault運用のリズムと噛み合わない場面があったとする体験談
   - **⚠️訂正（claude-code-guideで確認済み）**: 5時間のローリングウィンドウ制限は、**Claude for Teams/Enterpriseプランのみ**の仕組み（座席ごとの利用枠が5時間ローリング＋週次ウィンドウでリセットされる）。**Pro/Maxプランには5時間ローリング制限の記載は公式ドキュメントに見当たらず**、別の仕組み（プランごとの利用枠、週次リセットなど）が適用される。個人向けPro/Maxユーザー向けの記事で「5時間制限」と言い切っているのは、Teams/Enterpriseの仕様と混同している可能性が高い。
3. モデル更新（記事内ではOpus 4.7への言及）で、ツール呼び出し回数や推論の挙動が変化したと感じたという体験談
4. `.claude/skills/`のSkill発動が、複数Skillが競合すると期待通り動かないことがあったという体験談
5. Claude Codeは「コード生成」中心の設計思想であり、Markdown中心の知識整理用途には最適化されていないのではという問題提起

これらは**いずれも個人の運用体験に基づく主観的な課題感**であり、Anthropic公式の見解や仕様上の欠陥として確認されたものではない。

## Codex×Obsidian連携の技術的な仕組み（構造としては参考になる）

```bash
codex mcp add obsidian-mcp-tools
```

このMCP接続により、Codex CLIからObsidian Vaultへ直接アクセスし、「今日のworklogをObsidianに作って」のような指示が通るようになる、とのこと。Codexの場合、Skillは`~/.codex/skills/`に置き、`AGENTS.md`でVault内にルールを書ける、という設計思想が紹介されている。

## 紹介されていた運用アイデア（ツール比較とは独立して参考になる部分）

- **3層アーキテクチャ**: Raw（生素材）/ Wiki（構造化知識）/ Schema（型定義）の3層でVaultを構成する考え方
- **4サイクル運用**: Ingest（取り込み）→ Compile（構造化）→ Query（質問）→ Lint（矛盾チェック）という定型サイクル
- **ツール間でのSkill共有**: 複数のAIツールを併用する場合、共通スキルを`_shared-ai/skills/`のような共有ディレクトリに集約し、各ツール側からシンボリックリンク（junction）で参照する設計
- **役割分担の考え方**: 「軽量な処理（要約・分類・タグ付け）」と「品質クリティカルな処理（横断検索・矛盾検出・引用付き回答）」を別ツール・別フェーズに分ける、という発想自体は、[MCPツール自動化事例集](./mcp-tools-automation-50.md)や[Claude Codeモデル選択ガイド](./claude-code-model-selection.md)の「役割に応じてモデル/ツールを使い分ける」考え方と共通する
- **「コンパイラ兼司書」という比喩**: 素材を構造化する仕事（コンパイラ）と、構造化された知識に問い合わせて答える仕事（司書）を分けて考えるフレーム

## AIオフィスへの適用メモ

- 数値的な優劣比較は根拠が弱いため、**「どのツールが優れているか」の意思決定には使わない**。
- 一方で、「PKM/ナレッジベース運用を、取り込み・構造化・検索・監査の4サイクルに分ける」「軽い処理と品質クリティカルな処理でツール/モデルを使い分ける」「共通Skillを複数ツールから参照できるよう共有ディレクトリに集約する」という**設計パターン自体**は、既存の[AI社員7人体制](./ai-shain-7nin-claude-code.md)の`knowledge/`運用や、[Claude Codeモデル選択ガイド](./claude-code-model-selection.md)の使い分け方針と組み合わせて検討する価値がある。
