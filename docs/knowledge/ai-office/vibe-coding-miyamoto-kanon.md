# バイブコーディングの実践知見：宮本佳林さんの事例から

- **出典**: [元アイドルの天才バイブコーディング術【保存版】](https://note.com/sanko_55/n/ndfa174d2fa41)（アイアイ｜2児ママの現役SE, 2026年8月22日）
- **対象**: プログラミング未経験者がAIで本番システムを自走運用するための手順・チェックリスト
- **用途**: AIオフィスでの非エンジニア向けAI活用の検証工程・ガードレールとして参照する

## 要旨

プログラミング経験ゼロのアーティスト宮本佳林さんが、ChatGPT・Claude・Cursor・Claude Codeを役割分担して使い分け、プロモーションサイト・イベントアンケートシステム・10時間ノンストップ配信システムまでを個人開発・運用している事例。技術選定から入るのではなく「ユーザー体験を1つ決めてからAIに実装させる」という原則と、QAエンジニアが日常的に行う「検証」「相互監査」「フォールバック設計」を非エンジニアがどう組み込んでいるかが本題。

## 核となる原則

> AIに自分を作らせるのではなく、自分がやりたいことを実装できる組織能力をAIで個人に圧縮する

技術名やツールから入らず、まず「ユーザーが何をするか」を1つに絞って決め、その体験を具体化してからAIに仕様を作らせる。体験が明確なほど、AIへの指示も具体的になりブレない。

### モデルの役割分担

| フェーズ | ツール |
|---|---|
| 壁打ち（スマホ） | ChatGPT |
| 仕様の解像度を上げる | Claude |
| 実装（PC） | Cursor / Claude Code |

## 事例

1. **プロモーションを広告ではなく体験にする**（休日生態系診断, 2026年6月16日公開）
   - 楽曲プロモーションを広告収益化ではなく、診断コンテンツにMVを組み込んで楽しみながら接触してもらう設計。
   - 誤解を招くリスクがある診断コンテンツには免責事項を明記し、「エンターテインメント」であって医学・心理学的判断には使えないと境界線を引いている。
2. **感想収集を意思決定に変える**（イベントアンケート＋限定ボイス配信）
   - QR回答→限定ボイス視聴という参加インセンティブ設計。回答は翌日CSVで初参加/リピーター別にクロス集計し、セットリスト改善に反映。
   - 「満足度最適化だけを追って自分の表現したいものを失わない」という最終判断は人間側に残す方針を明言。運用は本人1人がスマホの管理画面から完結。
3. **10時間配信を止めなかったフォールバック設計**（2026年7月31日）
   - リアルタイムHUD、スマホ管理画面、X投稿数取得、AIによるMV再現度採点の4システムを本番10日前にClaude API決済が通らなくなりOpenAI APIへ緊急切替。AIベンダーへの依存箇所を限定した設計だったため、エンドポイントとリクエスト形式の変更のみで乗り切った。
   - X投稿数取得は精度が完全ではなかったが、失敗時は直前値を保持し管理画面から手動補正できる設計にしていたため、配信は一度も止まらなかった。
   - 教訓: **成功要因は精度そのものより「AIやAPIは失敗する」前提で人間の代替経路を用意していたこと。**

## そのまま使える手順

### 手順1: 仕様を壁打ちするときの質問リスト

AIに仕様を作らせる前に、この4点を埋める。

1. 誰が、どの端末から使うか
2. 何をする機能か（1つに絞る）
3. 成功したとき何が起きるか
4. 失敗したとき何が起きるか

### 手順2: 複数AIに相互監査させる依頼文

実装したAI自身に「レビューして」で終わらせず、別のAIに以下を依頼する。

> このコードとシステム構成について、次の3つの視点で問題点を挙げてください。
> 1. 攻撃者の立場で、壊せる箇所やなりすませる箇所はないか
> 2. 要件に対して、抜けている機能や例外処理はないか
> 3. APIキーやトークンなど、外部に漏れると困る情報が含まれていないか

同じAIによる自己レビューでは盲点が見えないため、別モデルに攻撃者視点で壊し方を探させる（脅威モデリングに相当）。

### 手順3: 自動化する前のフォールバックチェックリスト

- [ ] このAPIが失敗したとき、代わりに使う値や手段は決まっているか
- [ ] 自動処理（Cronなど）が最後に成功したのはいつか、確認する方法はあるか
- [ ] バックアップは「動いている想定」ではなく、実際にファイルが生成されているか確認したか
- [ ] 手動での代替操作（手入力・手動補正）は、非エンジニアでも数分でできる手順になっているか

## QAエンジニア視点での学び

- 「動いているはず」を鵜呑みにしない: 宮本さんのアンケートシステムでも、自動CSVバックアップが実は一部作動していなかったことが後日判明。手動保存を並行していたためデータ損失は回避できた。**AIがコードを書けることと、システムが正しく運用されていることは別問題。**
- 複数AI相互監査は「レビュー観点を変えた複数テストケース」と同じ発想。
- フォールバックを自動化より先に設計する順番自体がQAの基本姿勢。
- 社内提案時は「AIに作らせて終わり」ではなく、上記3手順を検証工程として組み込む提案が有効。

## 未解決・発展途上の課題（鵜呑み厳禁の領域）

- **セキュリティ/プライバシー**: 氏名・連絡先は取得せず、IP/ブラウザ情報はハッシュ化、Bot対策・レート制限は実施済み。一方でハッシュ方式・保存期間・再識別リスク評価・プライバシーポリシー整備は公開情報からは未確認。
- **著作権**: AIの学習データやクリエイター権利について本人も「まだ勉強が必要」と明言。Vision APIに映像フレームを送る構成のデータ取り扱いについても法的整理は未公開。
- 今後の課題として本人が挙げているのは、AWSコストの安全な管理、メール整理・重複確認などの手作業の自動化。

## AIオフィスへの適用メモ

- 非エンジニアがAIで本番運用まで行う際のガードレールとして、**手順1〜3をチェックポイント化**し、新規AI活用施策の立ち上げ時に必須ステップとして組み込むことを検討する。
- 「セキュリティ・プライバシー・著作権は発展途上」という誠実な公開姿勢自体が参考になる。自社でも技術選定理由の未理解・未検証automation・後回しのデータ保護という3つのリスクを定期的に棚卸しする運用を検討する。
