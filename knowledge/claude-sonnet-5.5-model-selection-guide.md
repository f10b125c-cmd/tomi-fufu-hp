# Claude Sonnet 5.5 の変更点と、3モデルの使い分けガイド

> 2026年9月28日発表。この記事は「まな式」記事と違い、公式発表・公式ドキュメントへのリンクが明記されており、内容の裏取りができる。claude-apiスキルの最新キャッシュデータ(2026-09-25)と照合したところ、**料金の倍率(Sonnet基準でOpus 2倍・Fable 5倍)は正確**だった。

## モデル選びの目安（3行）
- **Sonnet 5.5**：範囲の決まった日常業務を、速く進めたい
- **Opus 5.5**：複雑な条件を整理しながら、方針や設計を考えたい
- **Fable 5.1**：難しい推論や長期の作業で、Opusでも届かない課題に取り組みたい

迷ったら多くの用途でOpus 5.5から始め、難しい推論・長期作業ではFable 5.1を検討する、というのが公式ガイドの案内（[公式モデル一覧](https://platform.claude.com/docs/en/models/overview)）。

## Sonnet 5から変わった4つのポイント
1. **出力速度が30%以上向上**（Anthropic公表値）。短い依頼→結果確認→修正、の往復に向く。
2. **同じ仕事に使うトークンが減り、1タスクの費用が最大30%低下**。単価自体は据え置き（月額プランの値下げではない）。
3. **コード・画像理解などの実務性能が向上**（例：Terminal-Bench 4.0でSonnet 5の10.3%→5.5は70.6%、と記事は主張）。ただしベンチマークは特定条件での評価であり、自分のタスクでの再現性は別途確認が必要。
4. **文章がより明瞭に、対話しながらの共同作業がしやすく**なった。

## 使い分けの実践ガイド

### Sonnet 5.5：完成形が見えている仕事
文章の推敲、決まった項目のデータ整理、原因・修正範囲を絞ったバグ修正など。「ここまでやってほしい」が具体的なほど向く。
- ポイント：直してよい範囲を先に決める（例：「この文章をよくして」ではなく「事実は変えず、150字以内に整えて」）

**Sonnet用プロンプト例（事実を増やさず案内文を整える）**
```text
以下の材料だけを使い、社内向けの案内文を作ってください。

【目的】
AIをまだ使っていない人に、勉強会の内容と参加方法を伝える。

【材料：すべて架空】
・名称：はじめてのAI仕事術
・日時：10月8日 12:15〜12:45
・場所：第2会議室
・内容：メールの下書きと会議メモの整理
・持ち物：自分のパソコン
・参加方法：10月6日までに総務へ連絡

【条件】
・本文は150字以内。件名は本文と別に出す。
・専門用語は使わない。
・材料にない実績、効果、定員、料金を加えない。
・日程、場所、持ち物、参加方法を省かない。

【出力】
1. 件名
2. 案内文
3. 条件を満たせたかの確認結果
```
チェック観点：日時・場所・持ち物・参加方法が残っているか／150字以内か／材料にない情報を足していないか。AIの自己チェックだけで合格にしない。

### Opus 5.5：答えを出す前に考えることが多い仕事
複数案の比較、予算・人手・納期を同時に満たす設計、変更の全体影響調査など。「おすすめを教えて」で終わらせず、予算・人手・期限・避けたいリスクを渡す。

**Opus用プロンプト例（条件の違う改善案を比較）**
```text
小さなチームの業務改善について、今週試す案を1つ提案してください。
以下は架空の条件です。

【候補】
A：問い合わせへの返信の下書き。件数は多いが、顧客情報を含む。
B：会議メモから決定事項を整理。週1回。共有前に担当者が確認できる。
C：週次の売上集計。数値の転記が多く、ミスを減らしたい。

【制約】
・初月の追加予算は1万円以内。
・準備に使える時間は週2時間。
・新しい外部サービスへの顧客情報の入力は未承認。
・最初の1週間は、担当者が出力を確認してから使う。
・各案の作業時間と導入費用は、まだ調べていない。

【依頼】
1. 3案を、始めやすさ・確認負担・情報管理・測定しやすさで比較。
2. まず試す案と、その案を選ぶ条件を説明。
3. 判断に足りない情報を、重要な順に3つ挙げる。
4. 1週間の試行手順と、続ける／見直す基準を提案。

未知の費用や削減時間を作らず、「事実」「仮定」「提案」を分けてください。
```
チェック観点：条件によって結論が変わる「境目」まで説明されているか。きれいな企画書だけで終わっていないか。

### Fable 5.1：長時間考え続け、複数工程を進める難しい仕事
深い調査・分析、大きなコードベースをまたぐ開発、複数アプリを使う長時間作業。前の回答（Opus等）で解けなかった問題点を特定し、元資料と一緒に渡すのがコツ。ただし長時間作業はOpusも対応領域なので、毎回Fableから始める必要はない（Opusの思考深度を上げても基準に届かないときに検討）。

**Fable用プロンプト例（既存の計画案を根拠と矛盾から検証）**
```text
次の計画案について、根拠の不足、条件の矛盾、実行時の行き詰まりを検証してください。

【計画案】
[Opusなどで作った計画を貼る]

【根拠となる資料】
[資料ごとに名前を付け、本文を貼るか添付する]

【未解決点】
[前の検討でも解決していない問題を具体的に書く]

【必須条件】
[予算・期限・人員・情報管理など、変えてはいけない条件]

【完成基準】
[何を確認できれば、この計画を採用できるか]

【進め方】
1. 判断を左右する前提を洗い出す。
2. 各前提を、根拠あり／矛盾あり／資料不足に分ける。
3. 矛盾や不足のうち、結論に影響するものから検討する。
4. 条件を守る修正案と、それでも残る問題を示す。
5. 採用前に人が確認すべき項目を一覧にする。

根拠は資料名と該当箇所で示してください。
確認できないことを、解決済みと書かないでください。
検索やファイル操作が使えない場合は、その前提でできる範囲を明記してください。
```
※このプロンプト自体はOpusでも使える。Fable専用の魔法の文ではなく、「Opusで基準に届かないときに同じ課題で試して、改善したか確認する」ための比較用プロンプト。

## 工程ごとにモデルを使い分ける例（Webサイト改善のケース）
1. **Opus**で目的と課題を整理し、改善方針を決める
2. **Sonnet**で、方針が決まった文章・表示を修正する
3. 調査や検証が長引き、Opusでも解決できない部分があれば**Fable**を比較検討する

### モデルを切り替えるときのコツ
- 会話履歴を全部読ませる前提にせず、**目的・決まったこと・まだ解決していないこと・完了の条件を短く渡す**
  例：「対象は初めて来た人」「予約手順が分かりにくいので直す」「料金と予約条件は変更しない」「修正対象は案内文だけ」
- **切り替えすぎない**：数行の文章を直すたびに別モデルへ渡すと説明し直す手間が増える。判断の種類が変わった／同じ問題で止まった、が切り替えの合図。

## モデル比較のやり方（自分の仕事で試す場合）
同じ材料・同じ依頼を、新しいチャットに渡して比較する。見るのは3点：
1. 条件を守っているか
2. 根拠のない情報を足していないか
3. 自分の手直しがどのくらい必要か

回答が出るまでの時間と、確認・修正にかかった時間は分けて記録する（速く返ってきても修正に手間がかかるなら、仕事全体では速くない）。
